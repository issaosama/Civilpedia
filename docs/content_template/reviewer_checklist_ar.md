# قائمة مراجعة المحتوى الهندسي — للمراجع الهندسي

## مقدمة

هذه القائمة تستخدم من قبل المراجع الهندسي للتأكد من دقة وجودة المحتوى قبل اعتماده ونشره في تطبيق Civilpedia.

---

## 1. القيم الرقمية والحدود

- [ ] جميع القيم الرقمية صحيحة ومطابقة للمراجع المعتمدة.
- [ ] وحدات القياس مذكورة بشكل صحيح (مم، م، كجم، °C، إلخ).
- [ ] حدود القبول مذكورة بوضوح (مثل: 75-100 مم، لا يقل عن 60 قطر).
- [ ] التفاوتات المسموح بها (Tolerances) صحيحة ومطابقة للكودات.
- [ ] لا توجد قيم رقمية غير منطقية أو مستحيلة التطبيق.

## 2. المراجع والكودات

- [ ] جميع مراجع ASTM صحيحة (مثل: ASTM C143، ASTM A615).
- [ ] جميع مراجع ACI صحيحة وأرقام الأبواب مطابقة (مثل: ACI 318-19 §25.2.1).
- [ ] مراجع المواصفات البريطانية BS صحيحة إن وجدت.
- [ ] مراجع ISO صحيحة إن وجدت.
- [ ] المواصفات العراقية (إن وجدت) صحيحة ومحدثة.
- [ ] أرقام أقسام الكودات (section numbers) دقيقة.
- [ ] لا توجد مراجع قديمة أو ملغاة.
- [ ] الاقتباسات من الكودات دقيقة ولم يتم تحريف معناها.

## 3. وسوم [DRAFT - REVIEW REQUIRED]

- [ ] جميع وسوم `[DRAFT - REVIEW REQUIRED]` تم تحديدها في المحتوى.
- [ ] تم مراجعة كل وسم للتأكد من أن القيم صحيحة.
- [ ] الوسوم التي تم التحقق منها تم تحويلها إلى `[REVIEWED]` أو إزالتها.
- [ ] أي وسم متبقي يجب تبريره (لماذا لم يتم التحقق منه بعد).

## 4. المحتوى العام

- [ ] المعلومات دقيقة من الناحية الهندسية.
- [ ] المصطلحات الهندسية صحيحة ومستخدمة بشكل مناسب.
- [ ] الشرح المبسط (simpleExplanation) مناسب للمستخدم غير المتخصص.
- [ ] إجراءات ما قبل العمل (beforeWork) عملية وقابلة للتطبيق.
- [ ] إجراءات أثناء العمل (duringWork) صحيحة ومتسلسلة بشكل منطقي.
- [ ] إجراءات ما بعد العمل (afterWork) مناسبة.
- [ ] ملاحظات الموقع (siteNotes) مفيدة وتعكس الواقع العملي.

## 5. صيغة التقرير (Report Wording)

- [ ] صيغة التقرير واقعية ومناسبة للاستخدام في تقارير الموقع.
- [ ] تحتوي على متغيرات (مثل: (X)، (Y)، (Z)) للمستخدم لملئها.
- [ ] اللغة العربية سليمة وخالية من الأخطاء الإملائية.
- [ ] الصيغة لا تتعارض مع متطلبات العقد أو المواصفات.

## 6. معايير القبول والرفض (Accept/Reject)

- [ ] جميع معايير القبول والرفض واقعية وقابلة للقياس.
- [ ] حدود القبول محددة بوضوح (نطاق رقمي أو شرط واضح).
- [ ] المعايير الحرجة (`isCritical=TRUE`) هي فعلاً حرجة وتستحق التصنيف.
- [ ] طرق الفحص المذكورة مناسبة ومتاحة في المواقع.

## 7. الأخطاء الشائعة (Common Mistakes)

- [ ] جميع الأخطاء المذكورة هي أخطاء شائعة فعلاً في الموقع.
- [ ] مستوى الخطورة (`severity`) مناسب (low/medium/high/critical).
- [ ] طريقة التصحيح (إن وجدت) صحيحة وفعالة.

## 8. الأقسام والمقاطع

- [ ] جميع الأقسام مرتبة بشكل منطقي حسب `order`.
- [ ] أنواع المقاطع (block types) مناسبة للمحتوى.
- [ ] خطوات التنفيذ مرقمة بشكل صحيح ومتسلسل.
- [ ] نقاط الفحص مرتبة حسب الأهمية.
- [ ] الجداول تحتوي على البيانات الصحيحة والعناوين المناسبة.

## 9. الروابط والأدوات المرتبطة

- [ ] مسارات الأدوات المرتبطة (relatedToolRoutes) صحيحة.
- [ ] معرفات المواضيع المرتبطة (relatedTopicIds) صحيحة.
- [ ] لا توجد روابط مكسورة أو لمواضيع غير موجودة.

## 10. حالة سير العمل

- [ ] الحالة الحالية (`status`) مناسبة لمرحلة المراجعة.
- [ ] بعد المراجعة، يجب تحديث الحالة إلى `Engineering Review` (ثم `Approved` بعد الموافقة).
- [ ] قبل النشر، يجب أن تكون الحالة `Ready for App`.

## 11. التنسيق واللغة

- [ ] لا توجد أخطاء إملائية أو نحوية في النص العربي.
- [ ] المصطلحات الهندسية متسقة مع المعايير العربية المعتمدة.
- [ ] علامات الترقيم صحيحة.
- [ ] النص سهل القراءة وواضح.

---

## بعد الانتهاء من المراجعة

- [ ] إذا كان كل شيء صحيحاً: غيّر الحالة إلى `Engineering Review` وقدم للمعتمد.
- [ ] إذا وجدت أخطاء: سجل الملاحظات وأعد الحالة إلى `Draft` مع التعليقات.
- [ ] تحقق من إزالة أو اعتماد جميع وسوم `[DRAFT - REVIEW REQUIRED]` قبل `Ready for App`.
